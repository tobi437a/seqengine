# seqengine

A C++ engine for the Sequence card game (1v1 variant), with a pybind11
binding and a self-contained Python harness.

## Quick start

```bash
make python      # build the C++ engine + pybind11 module
cd python
python3 play.py  # GUI game against the engine; every game is logged to games/
```

`make python` needs a C++20 compiler, GNU Make, and `pip install pybind11`.

**Windows:** install GNU Make (e.g. via [MSYS2](https://www.msys2.org/) or
chocolatey's `make`), have `g++` from MinGW-w64 in PATH, then run the
same commands from PowerShell or cmd. The Makefile detects Windows and
swaps `python` for `python3`; shell operations go through Python helpers
in `tools/` so cmd.exe ↔ sh differences don't matter. If `python` isn't
on PATH but `py` is, run `make PY=py python`.

**macOS / Linux:** Xcode CLT or `g++`, plus `pip install pybind11`.

The rest of the project (C++ tests, benchmarks, validation) needs no
Python beyond the stdlib. Re-fitting the learned tables (`make fit`)
needs numpy and torch.

**The build targets the CPU it runs on** (`-march=native`): the engine
is popcount-heavy and is much slower without a hardware `POPCNT`. The
resulting binaries, including the `.pyd`/`.so`, may not run on an older
CPU. For something you can copy to another machine, build with
`make ARCH=-march=x86-64-v2`.

## Status

- **Engine:** bitboard state, move generation, sequence detection, dead-
  card mechanics, draw / reshuffle, win detection. Position evaluation
  (window-based Φ and shaping score, `src/eval.hpp`) is bit-identical to
  the Python reference: 300/300 positions and 1441/1441 shaping scores
  match within 1e-15, which is just IEEE round-off.
- **Search:** Single-Observer Information-Set MCTS (Cowling, Powley &
  Whitehouse 2012) with AlphaZero-style PUCT. One lock-free tree shared
  by all threads, edges keyed by the card played (not the hand slot),
  lazy expansion with FPU, tree reuse across moves, truncated rollouts.
  Move scores and the leaf evaluation are table lookups on per-window
  chip counts; the tables are fitted to the engine's own searches.
  Against a uniform-random opponent it wins 100 %; against the one-ply
  heuristic ~80 % at 2000 iters (200 games each).
- **Python bindings:** pybind11 module `_seqengine` with `MCTSConfig`
  and `MCTSEngine` classes. Wrapped by `python/mcts.py`'s
  `MCTSOpponent`, which matches the
  `(game, player, legal_mask) → action_int` signature used by all other
  opponents in this repo.
- **Tests:** all C++ unit tests pass (sequence detection corner cases,
  1000-game random self-play soak, MCTS tactical win, MCTS self-play
  smoke, tree reuse + multi-threaded search, and a self-check that the
  search's fast internal move generation / make-move / scoring agree
  with `GameState` and `eval.hpp`).

## Performance

From `make bench` on an 8-core / 16-thread dev box (Zen 4, `-O3
-march=native`):

| Workload                              | Throughput          |
|---------------------------------------|---------------------|
| `total_phi` (192-window eval)         | ~56M calls/s        |
| Random rollouts (full games)          | ~1.3M games/s       |
| Heuristic decision                    | ~17M decisions/s    |
| MCTS iterations, 1 thread             | ~160k iters/s       |
| MCTS iterations, 16 threads           | ~1.2M iters/s       |

The first three rows use all 16 threads. With the learned tables
switched off (`learned_policy = learned_value = false`) the search runs
~300k iters/s on one thread and ~2.0M on 16; see *MCTS design* §12 for
what that trade buys.

The MCTS rows average searches over 40 sampled mid-game positions. The
initial position alone is slower because the tree is at its widest
there.

## Using the engine from Python

```python
from game_engine import SequenceGame
from seq_actions import get_legal_action_mask, int_to_action
from mcts import MCTSOpponent

mcts = MCTSOpponent(iterations=20000)

game = SequenceGame()
game.reset()

while not game.done:
    player = game.current_player
    mask = get_legal_action_mask(game, player)
    action = int_to_action(mcts(game, player, mask))
    card = game.hands[player][action[0]]
    game.step(action)
    mcts.advance(action, card)      # optional: lets the next search reuse the tree
```

`MCTSOpponent.__call__` accepts the same `(game, player, legal_mask)`
signature as `heuristic_action` and `random_action`, so it drops straight
in as a swappable opponent. The legal-mask is ignored (MCTS re-derives
legal moves from its own bitboard state) but is part of the signature for
compatibility with the rest of the harness.

`MCTSOpponent` uses every hardware thread by default (`n_threads=0`).
`engine.last_stats()` reports iterations, depth, time, the chosen move's
win estimate, and how many visits were carried over from the previous
search.

## MCTS design

Single-Observer Information-Set MCTS (Cowling, Powley & Whitehouse
2012). Public-info perfect-information MCTS, made hidden-info-aware via
per-iteration determinization:

1. **Per-iteration determinization.** ONE tree shared across all
   iterations; every iteration freshly deals the opponent a random hand
   from the cards we haven't seen, then walks the tree using only
   children whose move is legal in the current determinization. Tree
   nodes store *moves*, not states; the live state is rebuilt by
   replaying moves from the determinized root each iteration. A single
   search budget sees as many distinct guesses of the opponent's hand
   as it has iterations, which directly addresses *strategy fusion* —
   the failure mode where the search commits to a plan optimized for
   one (wrong) guess of the hidden information. The deck is never
   shuffled: its order is hidden too, so whenever a card is drawn inside
   the search it is simply a random one of the remaining cards.

2. **Moves are cards, not hand slots.** A tree edge is "two-eyed jack
   on cell 37" or "the card for cell 52", never "hand slot 3". Slots are
   an accident of hand order: the opponent's hand is re-dealt every
   iteration, so slot-keyed edges split one opponent move over up to
   seven children, and two copies of a card in our own hand split one
   move — and its visits — over two. `GameState::legal_moves` likewise
   returns each distinct (card, target) once. It also means the board
   at a node depends on the path alone, and that a harness can report
   an opponent's move for tree reuse without knowing their hand.

3. **PUCT selection with a prior.** Selection maximizes
   Q(a) + c · P(a) · √(Σ_b N(b) + 1) / (1 + N(a)), where the prior
   P(a) is a softmax over each legal move's score (§12), recomputed
   per descent step (hands diverge across determinizations). The visit
   sum runs over the *currently-legal* children only, so moves legal in
   few determinizations aren't unfairly punished — the concern classic
   ISMCTS handles with per-child availability counts, folded into PUCT
   here. Ties are broken uniformly at random.

4. **Robust-child final selection.** Argmax visits over root children
   (not argmax mean). Visit count is the more stable signal because it
   incorporates the bandit's own confidence in its estimates.

5. **ε-greedy rollouts.** The rollout policy takes the best-scoring
   move with probability 1−ε (default ε=0.30) and otherwise a random
   one. Pure greedy makes every rollout from a state identical and
   defeats MCTS. A random ply chooses among the *non-jack* moves: a
   two-eyed jack accounts for ~90 of ~105 legal moves, so a uniformly
   random ply would throw it away nearly every time one is in hand
   (`cfg.random_ply_jacks = true` restores that). Worth **+33 Elo**
   (800 pairs, CI +21..+46).

6. **Length-decay knob.** `cfg.length_decay` (default 1.0 = off) lets
   you prefer fast wins / slow losses by setting it `< 1`. It gives no
   overall winrate benefit, but it's useful for tactical sanity tests
   where multiple winning continuations tie at +1.0.

7. **Lazy expansion with FPU.** Selection runs PUCT over *all* legal
   moves at a node: visited children use their empirical Q, unvisited
   moves use a first-play-urgency value of parent-Q −
   `cfg.fpu_reduction` (default 0.10), and a node is only materialized
   when actually selected. Force-expanding every legal move first
   burns most of a small budget sweeping width-first.

8. **Tree reuse across moves.** (`cfg.tree_reuse`, default ON.) The
   engine keeps its tree between `suggest_move` calls. The harness
   reports each actually-played move via `MCTSEngine::advance(state,
   move)` (or `advance_card(card, cell)`); the next search re-roots the
   tree at the node matching the played path, carrying over the
   subtree's statistics. If the path has no node — or `advance` was
   never called — the search starts from an empty root. From Python,
   call `MCTSOpponent.advance(action, card)` for every played move
   (`play.py` does).

9. **One shared tree, many threads.** `cfg.n_threads` workers all
   search the same tree, lock-free: nodes come from a preallocated
   arena via an atomic bump index, a node's children are a linked list
   that new children are prepended to with a compare-and-swap, and
   statistics are atomics. Virtual loss keeps simultaneous descents
   from piling onto one line. The C++ default is `n_threads=1`, which
   is deterministic given a seed (tests, benchmarks and the match tools
   rely on that); the Python wrapper defaults to every hardware thread.
   `make ablation` measures what sharing costs: 16 threads against 1
   thread at 10000 iterations each scored 28–32 over 60 games (no
   measurable loss) at 8.4× the iterations per second.

10. **Truncated rollouts.** (`cfg.rollout_cutoff`, default 12.) A
    rollout still running after 12 plies stops and is scored
    statically (§12). Set `rollout_cutoff = 0` for full playouts.
    Shorter rollouts are cheaper and the static evaluation is lower-
    variance than a long ε-greedy playout: +62 Elo at 800 iterations
    and +34 at 4000 against full playouts.

11. **Where the search's scoring departs from `eval.hpp`.** The
    reference evaluation stays as it is (it is what the Python side and
    the one-ply heuristic use); the search scores a few things
    differently, each behind a config flag:
    - *Dead windows* (`cfg.dead_windows`). A new sequence may share at
      most one chip with an existing one, so a window holding two or
      more of a player's locked chips can never complete. Φ still
      counts the finished sequence as a "5" and the windows one step
      along the line as "4"s — which rewards the opponent for
      "blocking" a line that was never a threat. The search scores
      such windows as zero.
    - *Completing a five* (`cfg.shaping_seq_bonus`, hand-tuned scores
      only). The shaping score of the move that completes a sequence is
      ≈ −0.03 from that window (the 4 → 5 weights are equal), so
      without a bonus rollout players walk past their own sequences.
    Both together: **+26 Elo** (800 pairs, CI +14..+40).

12. **Learned tables.** (`cfg.learned_policy`, `cfg.learned_value`,
    default ON.) A move's score is a sum of one table entry per
    5-window through its cell, and a position's value a sum of one
    entry per window on the board; the entry depends only on the
    window's state — joker or not, my chips, their chips — and the game
    stage (who already has a sequence). The search keeps one byte of
    state per window up to date as moves are made, so both are plain
    lookups. With the flags off, the entries are computed from
    `eval.hpp`'s weights (plus `jack2_value` / `jack1_value` for jacks
    in hand, and the tanh(`cutoff_scale` · …) squash). With them on,
    they come from `src/learned_tables.hpp`, which `make data` +
    `make fit` produce:
    - *move scores* are fitted so that softmax(score) over a position's
      legal moves matches the visit distribution the search itself
      produced there; they also see the mover's hand — a line whose
      remaining cells the mover holds cards for scores higher;
    - *value* is a logistic regression of the game's winner (blended
      with the search's root value) on the window counts, jacks in
      hand and side to move.
    Against the hand-tuned tables at equal iterations: **+23 Elo** at
    3000 iterations (1200 pairs, CI +13..+32) and +9 at 20000 (400
    pairs, CI −5..+23). Iterations take about 1.8× as long with them —
    the sharper prior drives the tree deeper — so at equal *time* the
    two are close; turn the flags off if you'd rather have the speed.

### What the measurements say about this game

All from paired self-play (same deal, seats swapped), 3000 iterations
unless noted:

- **Luck dominates.** Around three quarters of game pairs are split
  1–1: the deal decides, whoever plays it. An engine that is allowed to
  *see the opponent's hand and the deck order* gains only +75 Elo. So
  expect every real improvement to look small in Elo.
- **More search helps, with diminishing returns.** 500 → 2000
  iterations: +27 Elo; 2000 → 8000: +23; 8000 → 32000: +9 (within
  noise). How far the curve climbs depends on the rollout policy: with
  §5's and §11's fixes off it is already flat at 2000.
- **The tree below the first move barely matters.** Replacing the
  opponent's in-tree replies with plain samples from the prior changes
  nothing measurable, and neither does splitting the budget over 8
  independent trees. The engine is close to a one-ply
  Monte-Carlo evaluator, which is why what the *rollouts* do is where
  the strength came from.

### Rejected alternatives

- **γ-discounted sum of step rewards as rollout value** — variance
  dominates signal. The dense reward signal sounds right in principle
  but is strictly worse than terminal ±1 in head-to-head.
- **Partial-credit terminal value** (terminal + α · Δseqs at end of
  rollout) — same problem; marginal at best.
- **Always taking a sequence-completing move in rollouts** — harmful
  as a hard override on full-length rollouts. The soft version (a
  score bonus, §11) is what works.
- **A bonus for blocking an open four**, a larger completion bonus
  (8 instead of 4), a sharper prior, shorter (6) or longer (20)
  rollouts, ε = 0.15, c = 1.2 or 3.0 — all within noise of the defaults
  or slightly worse.
- **Sampling rollout moves from softmax(score)** instead of ε-greedy —
  no better per iteration and ~40 % slower.
- **Root-parallel trees** (N independent trees, root visits summed) —
  8 trees and 1 tree play equally at equal total iterations, so nothing
  is lost by putting all threads on one, and one tree is simpler.

The common thread: in MCTS, lower-variance value estimates beat
denser-but-noisier ones.

## Other design notes

### Bitboards

100 cells don't fit in one `uint64_t`, so `BB100` is a pair: `lo` (cells
0..63) and `hi` (cells 64..99 with the top 28 bits masked off). Standard
ops: `|`, `&`, `~`, `popcount`, `test/set/reset`, plus `pop_lsb` for
iterating set bits.

Per-player state lives in two pairs of bitboards:

- `chips[2]`  — unlocked chips per player
- `locked[2]` — chips claimed by a completed sequence (immune to
  one-eyed jacks; can be re-used by a second overlapping sequence
  via the "share ≤ 1 chip" rule)

Joker corners aren't stored in any of these — they live in the static
`JOKER_MASK` and count as "everyone's chip" for sequence purposes.

### Sequence detection

The 192 possible 5-in-a-row windows are precomputed as `BB100` masks, and
each cell has a precomputed list of the ≤20 window indices passing
through it. When a chip is placed at cell `c`, sequence detection only
inspects those windows. Iteration order (direction-major, then position)
matches `game_engine.py`'s `_check_sequences` exactly, because earlier
windows in a single call can lock chips that disqualify later candidate
windows under the share-≤1 rule.

### Window bytes

Inside the search every window also has one byte, `36·joker + 6·n0 +
n1` (plus a flag once it is dead), updated for the ≤20 windows through
a cell whenever a chip lands or leaves. Scoring a move, evaluating a
position and noticing that a placement made five are all lookups on
those bytes — no bitboard work in the rollout loop. `search_selfcheck`
(run by `make test`) replays random games checking them, the search's
move generator and its make-move against `GameState` and `eval.hpp`.

### Codegen

Board layout (suit assignments, joker corners, card→cells map) lives in
`python/board_layout.py` and isn't worth maintaining by hand on the C++
side. `tools/gen_board_data.py` reads it and emits the C++ tables. Run
`make codegen` after editing the board.
